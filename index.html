Architecture brief · Entitlements for AI agents in a bank

Governance that learns: self-hardening entitlements for AI agents

A bank with 160+ systems and agents already working across them needs to answer one question on every agent action: should this agent do this, on this system, on whose behalf? This design answers it with plain code at run time, and keeps the rules current with an AI loop that attacks and repairs them before a real attacker does.

One message: every new attack technique automatically becomes a new control, and the business cost of each control is shown before anyone signs off.
1 · The architecture

Two planes: a run-time plane that enforces, and a learning plane that improves the rules

Deterministic code (makes every allow/deny decision) AI agent (proposes, attacks, inspects) Human sign-off Existing bank systems and agents
2 · One agent action, step by step

What happens when the Sales agent asks the Banking agent for deal details

1
The request arrives with an identity. The salesperson signs in; the Sales agent acts with the salesperson's identity attached. Production: SSO token passed on with OAuth 2.0 token exchange (RFC 8693), so every hop knows the original person.
2
Sales calls the Banking agent. That call goes through the gateway too. The gateway records the chain: person → Sales → Banking.
3
Banking tries to read the deal record. The gateway checks the policy for every party in the chain, not only Banking. Sales is not allowed to read deals, so the call is denied. This is the "intersection" rule the designer agent added after the confused-deputy breach in our run.
4
If the agent had read external content earlier (for example a client email), any outbound action after that is held for a human. Untrusted-content flag carried with the session.
5
Before anything leaves the bank, an AI content check scans the outgoing message for confidential deal information, even if disguised as a code name. It can only block, never allow something the rules denied.
6
Everything is logged: who asked, on whose behalf, which tool, the decision, and the policy version that made it. The same log feeds the breach check in the learning plane.
3 · The learning loop

The arms race, round by round

The red team is not given a script. It is given the bank's rules and told to find a new way to break any of them each round. The rows below are the attack families the sandbox is built to allow. Which ones the red team actually finds is the result of the run, not a script.

RoundAttack familyExample in this bankControl the designer can applyWhy simple on/off rules fail
0No rulesAny agent reads the secret dealLeast-privilege access rules from the tool lists—
1Confused deputySales gets the deal via the Banking agentRights of everyone in the call chain must agreeBanking's own access is legitimate
2Poisoned external contentA "client" email tells Sales to forward a draft or place a tradeUntrusted-content flag: later outbound actions need a humanSales must read client email to do its job
3Disguised leakBanking spells the buyer as a code name in an emailAI outbound content check (block only)Keyword filters miss paraphrase and code names

Stopping rule: the loop ends when the red team fails several rounds in a row and every business task still passes. Each round records the new attack, the fix, and the capability cost.

5 · Questions leadership will ask

Answers to have ready

Is an AI deciding who can access our data in production?

No. Every allow or deny is made by plain code reading a versioned policy. AI proposes policy changes in a sandbox, and a human approves them before they go live. The only AI in production is the outbound content check, and it can only block.

Does the attacking agent touch our real systems or data?

No. The red team works in a sandbox copy with synthetic or masked data. It attacks the policy, not the bank.

How does this scale to 160+ systems?

Step 0 reads each system's tool list (what an agent can call on it) and tags every tool by system, read or write, and data sensitivity. The designer agent drafts least-privilege rules from those tags and each agent's job description. Systems without an MCP interface get a thin adapter in front of their existing API. Rules are grouped by agent role, so they do not grow one-per-system by hand.

What if the fixes lock things down so much that the business stops working?

Every proposed change is re-run against the business task suite. A change that breaks a task is flagged with its exact cost, for example "client briefings now need human approval", before anyone signs off. The trade-off is shown, not hidden.

How is this different from our existing IAM and role-based access?

IAM answers "can this identity reach this system". Agents add three new problems: one agent acting for another (confused deputy), agents obeying instructions hidden in data they read, and leaks through legitimate channels. This layer sits on top of IAM and handles those. Human roles carry through: an agent acting for a person gets only what both are allowed.

What if the red team is not creative enough?

It uses a stronger model than the business agents, sees which techniques were blocked so it must try new ones, and can be seeded with published attack catalogues such as the OWASP Top 10 for LLM applications. Human red teamers can add attacks to the same replay library, so every attack ever found is re-tested on every policy change.

How do we prove to auditors and regulators what happened?

Every agent call is logged with the person, the agent chain, the tool, the decision and the policy version. Every policy version records the attack that triggered it, the fix, the test results and who approved it.

What happens if the gateway fails?

It fails closed: no decision means no action. A bad policy is rolled back to the previous approved version.

What does it cost to run?

Today's proof run made 156 model calls for about $0.04 (₹4) on a small model. The gateway itself is ordinary code with no per-call model cost. The learning loop runs on a schedule or when a new agent or system is added, not on every request.

Where does it run? Our data cannot leave our environment.

All components can run inside the bank's own cloud tenancy, with whichever approved model provider the bank already uses. The demo used Straive's LLM Foundry.
